## 2. Retrieval: чому саме так

**Задача:** тікети приходять різними мовами (uk, ru, es, de, pl, транслітом), а база знань — англійською. Пошук «у лоб» за словами тікету не знайде статтю *Refund policy* за запитом «поверніть гроші».

**Рішення: LLM-переформулювання запиту + BM25 + буст за категорією.**
1. Крок `analyze` перетворює тікет будь-якою мовою на 1–3 **англійські пошукові запити** («duplicate subscription charge», «refund duplicate payment»).
2. **BM25** (класичне ранжування за ключовими словами) шукає по 17 статтях. Для статті береться найкращий score серед запитів.
3. Статті тієї ж категорії, що визначив класифікатор Task 1, отримують **буст ×1.3**: гібрид «ключові слова + намір клієнта».
4. У генерацію йдуть **топ-3 статті**. Модель може цитувати лише їх, а код перевіряє, що цитата **дослівно** є в статті.

**Чому не embeddings + vector DB:**
- Groq не має API для embeddings. Локальні embedding-моделі тягнуть PyTorch (~2 ГБ) — зайвий ризик для прототипу на Windows і для деплою на Streamlit Cloud.
- На 17 статтях з англійським запитом від LLM BM25 дає **hit@3 = 94%** (див. розділ 6). Головну слабкість BM25 — синоніми й інші мови — вже закриває LLM-переформулювання.
- BM25 прозорий: видно, чому знайшлась стаття (score в UI), легко дебажити.

**Відома слабкість BM25 і що з нею зроблено:** BM25 **завжди** щось повертає, навіть коли відповіді в базі немає (тікет #18 про друковану книгу гороскопів знаходить статтю про push-сповіщення через слово «horoscope»). Поріг score тут не працює — score відносний. Тому в `generate_v2` модель окремо оцінює `kb_coverage: full | partial | none`, і при `none` UI показує «у базі знань немає відповіді».

**Для production:** embeddings (мультимовні) + vector DB, гібридний пошук (BM25 + dense), реранкер, chunking довгих статей, метрики hit@k на реальних тікетах із розміченими «правильними» статтями.

## 3. Промпт і різні тони

**Один виклик — три тони в одному JSON.** Альтернатива — три окремі виклики, по одному на тон — коштує втричі більше і гірше тримає **узгодженість фактів**: три незалежні генерації можуть дати різні строки чи кроки. В одному виклику модель спершу «вирішує», що сказати, а потім формулює це трьома способами.

Структура `generate_v2` ([prompts/generate_v2.md](prompts/generate_v2.md)):
1. **Роль і контекст:** агент перегляне й відредагує чернетку.
2. **Hard rules для всіх тонів:** мова клієнта; лише факти зі статей; **жодних обіцянок refund / компенсацій / результату**; запитати відсутню інформацію; не просити CVV; не віддзеркалювати агресію; не оцінювати експерта до перевірки; без emoji; підпис «команда підтримки Nebula».
3. **Специфікація кожного тону — вимірювана, а не «будь формальним»:**

| Тон | Що вимагає промпт |
|---|---|
| **formal** | ввічливе «Ви», повні речення, без окличних знаків і розмовних слів; структура: привітання → підтвердження запиту → інформація → що далі → завершення; 60–120 слів |
| **empathetic** | **перше речення називає конкретну ситуацію й почуття клієнта** (не шаблонне «вибачте за незручності»); тепло, але без «Привіт!» і сленгу; 70–130 слів |
| **short** | ≤ 3 речення і ≤ 45 слів; лише суть і наступний крок; ті самі правила щодо обіцянок |

4. **«Три варіанти містять однакові факти і кроки — відрізняються лише тон і довжина».**
5. **Цитати і `kb_coverage`.**
6. **Тікет у тегах `<ticket>`** + інструкція не виконувати команди з нього (prompt injection).

`temperature = 0.4` для генерації (трохи природності мови), `0` для repair-запиту і всіх інших кроків.

Що не спрацювало з першого разу і як еволюціонував промпт — у **[PROMPTS.md](PROMPTS.md)**.

## 4. Поганий AI-output і як я це вирішив

### Приклад: неявна обіцянка повернення коштів

**Тікет #8** (en): *«I was charged twice, refund me or I'll dispute with my bank.»* Промпт `generate_v1`, модель gpt-oss-120b, емпатійний варіант:

> *Hi there, I'm really sorry to see you've been double‑charged – that must be frustrating. Could you send us the last 4 digits of the card, the dates and amounts of the two charges…? With that info, **our Billing team can check the duplicate and get a refund processed for you as quickly as possible.***

**Чому це погано:**
- Це **обіцянка повернення коштів**, хоча рішення ухвалює Billing лише після перевірки. Якщо другий платіж — тимчасова авторизація банку (стаття `double-charge`: вона зникає сама за 3–5 днів), повертати нічого. Клієнт отримав обіцянку, а потім відмову → гірше, ніж чесне «перевіримо».
- **Детермінована перевірка це пропустила:** regex шукає явні фрази («we will refund you», «повернемо кошти»), а тут обіцянка схована в «get a refund processed for you». Перефразувань — нескінченно.
- Бонус: *«Hi there»* — фамільярно для тікету з погрозою chargeback.

**Як вирішив — три рівні захисту, бо жоден окремо не надійний:**
1. **Промпт (`generate_v2`)** — заборона обіцянок **з прикладом межі**: *«Even "so we can return the extra payment" is a promise»* + що писати натомість: *«our payments team will review the charge and get back to you»*. Приклад межі потрібен, бо обіцянки в v1 були **неявні** («get a refund processed for you») — абстрактне «не обіцяй refund» модель могла б вважати виконаним.
2. **Код** — regex обіцянок 5 мовами ловить явні випадки → ⚠️ review з причиною «знайдено обіцянку refund».
3. **Інтерфейс — головне:** для **будь-якого** тікету категорії `refund_request` рівень ⚠️ review ставиться **незалежно від тексту відповіді**, з причиною «рішення про повернення ухвалює Billing», і копіювання заблоковане до галочки «Я перевірив(ла)». Тобто навіть якщо промпт і regex обидва пропустять обіцянку, агент **не може** відправити чернетку не прочитавши її.

**Результат:** у `generate_v2` той самий тікет #8 (gpt-oss-120b): *«Our billing team will review the information and, if a duplicate is confirmed, will process a refund»* — обіцянка стала **умовною** й відповідає статті `double-charge` («Confirmed duplicate charges are always refunded in full»), «Hi there» зник. Але **не ідеально**: наступне речення — *«after which the refund will be returned to the original payment method»* — знову звучить як гарантія. Саме тому третій рівень (блокування копіювання) лишається обов'язковим: промпт зменшує частоту, але не гарантує. Детерміноване порівняння v1 і v2 на тих самих тікетах — [results/prompt_comparison.md](results/prompt_comparison.md).

Інші знайдені проблеми v1 (вигадана «digital version» для тікету поза базою знань, неповний «короткий» варіант, англійські назви команд в українських відповідях, недослівні цитати) і як їх вирішував — у [PROMPTS.md](PROMPTS.md).

## 5. Межі автоматизації: де рішення приймає агент

### Сценарії, де human judgment обов'язковий

| # | Сценарій | Логіка | Що робить інтерфейс |
|---|---|---|---|
| 1 | **Кризовий стан клієнта** (суїцидальні думки, самоушкодження) | Ціна помилки — життя. Шаблонна чи «продажна» відповідь може нашкодити; протокол вимагає живої людини і кризових контактів | ⛔ **blocked**: генерація навіть не запускається, AI-варіанти приховані, показано протокол зі статті |
| 2 | **Повернення коштів / спірні списання** | Фінансове рішення: треба перевірити транзакцію, магазин (Apple/Google), історію повернень. AI не бачить платіжної системи | ⚠️ review + перевірка в коді на обіцянки refund |
| 3 | **Юридичні погрози, chargeback, регулятори** | Будь-яке формулювання може стати доказом; не можна визнавати провину | ⚠️ review, причина: «не визнавати провину, ескалювати Legal» |
| 4 | **Скарги на експерта, особливо фрод і харасмент** | Звинувачення конкретної людини; рішення — після перевірки логу чату. AI не може «вирішити», хто правий | ⚠️ review, причина: «не оцінювати експерта до перевірки» |
| 5 | **Видалення / експорт персональних даних** | Незворотна дія + треба верифікувати, що пише власник акаунта (інакше витік даних) | ⚠️ review |
| 6 | **P1 будь-якого типу** (масовий збій тощо) | Критичний тікет може вимагати ескалації, а не відповіді | ⚠️ review |
| 7 | **У базі знань немає відповіді** (`kb_coverage = none` або немає статей) | AI без джерела = ризик вигаданої політики | ⚠️ review, «не покладайся на AI-варіанти» |
| 8 | **Перевірка в коді знайшла проблему** — цитати немає в статті, обіцянка refund, не та мова | Конкретний доказ, що чернетка може бути хибною | ⚠️ review з конкретною причиною |
| 9 | **AI не впевнений** (`confidence < 0.6`, категорія `other`) | Модель сама не розуміє тікет | ⚠️ review |

### Як це позначено технічно

- **Три рівні з різною «тертям»:** ✅ `ok` — зелений банер, копіювання одразу. ⚠️ `review` — жовтий банер зі **списком конкретних причин** + **кнопка копіювання заблокована**, поки агент не поставить галочку «Я перевірив(ла) факти й причини вище». ⛔ `blocked` — червоний банер, **варіантів немає зовсім**.
- **Причини формує код, а не модель** ([assistant.py → `human_judgment()`](assistant.py)): AI не може «переконати» UI, що все гаразд.
- **Цитати з позначкою:** ✅ «дослівно є в статті» / ❌ «цитати НЕМАЄ в статті» — агент бачить, на чому базується відповідь.
- **Бейджі** пріоритету (кольором), категорії й команди — агент одразу бачить контекст.
- **Для production:** логувати, яку версію агент обрав і наскільки відредагував (edit distance) — це найкращий сигнал якості промпту; галочку «перевірив» прив'язувати до ID агента (аудит).

## 6. Evaluation

### Тестовий набір

[data/test_set.json](data/test_set.json) — **18 тікетів**, 7 не англійською (uk, ru, es, de, pl, транслітерація). Для кожного розмічено: правильні статті бази знань, категорія, пріоритет і **очікуваний рівень human judgment** (`blocked` / `review` / `ok`). Покриті: refund, подвійне списання, скасування, погроза chargeback, кризовий стан, фрод і скарга на експерта, видалення даних, технічні збої, промокод, агресія, сарказм і **#18 — питання, на яке в базі знань немає відповіді**.

### Що і як міряється

| Метрика | Як | Хто перевіряє |
|---|---|---|
| Retrieval hit@1 / hit@3 | правильна стаття на 1-му місці / в топ-3 | код |
| Категорія, пріоритет | збіг з розміткою | код |
| Human-judgment level | рівень `blocked/review/ok` збігся з очікуваним | код |
| Цитати | цитата **дослівно** є в статті | код |
| Мова, довжина, emoji, явні обіцянки refund | langdetect, підрахунок слів, regex | код |
| Grounded, неавторизовані обіцянки, відповідає на запит, кожен тон «ок», різниця тонів 1–5 | LLM-суддя за [prompts/judge_v1.md](prompts/judge_v1.md) | qwen3.8-27b (інша родина моделей, ніж кандидати gpt-oss) |
| **Quality pass** | суддя: все ✅ **і** всі цитати дослівні | разом |

### Результати

### Знахідка: LLM-суддя ненадійний для тонких критеріїв

Одні й ті самі відповіді `generate_v1` я оцінив двома суддями ([results/generate_v1_judge-gpt-oss-120b/](results/generate_v1_judge-gpt-oss-120b/summary.md) і [results/generate_v1/](results/generate_v1/summary.md)):

| Модель генерації | Суддя gpt-oss-120b | Суддя qwen3.8-27b |
|---|---|---|
| gpt-oss-120b | 94% *(самооцінка)* | 88% |
| qwen3.8-27b | **35%** | **88%** *(самооцінка)* |

Розбіжність у 53 п.п. на **тих самих текстах** — переважно через критерій «короткий тон ок». Кожен суддя **м'якший до своєї моделі**. А тонкі проблеми (неявна обіцянка refund у #8, фамільярне «Hi there», англійські назви команд) **не помітив жоден** суддя: з одним суддею v1 і v2 на 120b виглядають однаково (9 з 10 спільних тікетів). Тому:
- різницю між v1 і v2 я міряв ще й **детерміновано, кодом** ([compare_prompts.py](compare_prompts.py) → [results/prompt_comparison.md](results/prompt_comparison.md)): на 10 спільних тікетах gpt-oss-120b фамільярний тон 4 → 0, англійські назви команд 1 → 0, не та мова 1 → 0, неявні обіцянки 2 → 1. Погіршення: у 2 тікетах короткий варіант трохи довший за новий ліміт 45 слів (46 і 49);
- усе, що можна перевірити кодом, перевіряється кодом **у продукті**, а не лише в eval;
- у production суддю треба калібрувати на 50–100 відповідях, оцінених агентами, і використовувати лише для **відносного** порівняння версій.

## 7. Порівняння моделей і вибір

Порівнював три моделі на Groq у ролі **генератора** (класифікація й аналіз — gpt-oss-20b, як у Task 1).

| | gpt-oss-20b | **gpt-oss-120b** | qwen3.8-27b |
|---|---|---|---|
| Quality pass, v1 (суддя qwen) | 70% | **88%** | 88% *(самооцінка)* |
| Quality pass, v1 (суддя 120b) | 67% | 94% *(самооцінка)* | 35% |
| Quality pass, v2 (суддя qwen) | 78% | **90%** | не прогнано |
| Latency генерації | 1.8–2.5 с | 2.3–3.6 с | 1.5 с |
| $ / 10k тікетів (весь конвеєр) | $6.82 (v1) / $8.88 (v2) | $9.24 (v1) / **$13.24 (v2)** | $29.37 (v1) |
| Статус на Groq | production | production | preview |

**Вибір: gpt-oss-120b для генерації, промпт v2; fallback — gpt-oss-20b.**
- **Якість:** 120b стабільно найкращий з gpt-oss з будь-яким суддею (+12–27 п.п. до 20b). У Task 1 більша модель виграшу не дала, а тут дає: класифікація — це вибір з 9 варіантів, а генерація трьох тонів мовою клієнта з дотриманням правил — значно складніша задача.
- **Ціна:** різниця з 20b — **~$4 на 10 тисяч тікетів на місяць**. Одна відповідь, яку агенту не треба переписувати, економить хвилини його часу — це на порядки дорожче.
- **qwen3.8-27b — ні:** ×2–3 дорожче, статус preview, і його якість залежить від судді (35% vs 88%), тобто результат не підтверджений незалежно. v2 на qwen не проганяв: його добова квота потрібна для ролі судді.
- **Чому v2 дорожчий за v1:** довший system prompt (правила + специфікації тонів) і довші, структуровані відповіді. +$4 / 10k — прийнятна ціна за прибраний фамільярний тон, англійські назви команд і `kb_coverage`.
- **Мала модель для класифікації й аналізу, велика — лише для генерації:** дорожча модель стоїть лише там, де вона дає якість.
- В інтерфейсі модель можна перемкнути в сайдбарі — для порівняння наживо.

## 8. Failure handling

Спільний [common/llm_client.py](../common/llm_client.py) з Task 1 (retry з backoff і `retry-after`, repair невалідного JSON, перевірка схеми pydantic, fallback-ланцюжок моделей) плюс специфічне для Task 2:

| Збій | Поведінка |
|---|---|
| **Rate limit / timeout** на генерації | retry → fallback `gpt-oss-120b → gpt-oss-20b`. Якщо обидві впали — UI: «AI не зміг згенерувати відповіді, напиши вручну, статті нижче». Summary і статті все одно показуються |
| **Крок `analyze` впав** | пошук іде прямо за текстом тікету; summary «(AI-аналіз недоступний)»; генерація продовжується |
| **Класифікатор впав** | Task 1 повертає `source=fallback`, `needs_human_review`; safety- і legal-guardrails працюють без LLM |
| **Invalid JSON / порушена схема** (немає одного з тонів, порожній текст) | repair-запит → наступна модель |
| **Цитата, якої немає в статті** (галюцинація) | 1 repair-запит з переліком хибних цитат; якщо знову хибна — цитата показується з ❌ і банер «перевір факти» |
| **Обіцянка refund у тексті** | не блокує, але ⚠️ review з поясненням |
| **Rate limits безкоштовного тарифу** | безкоштовний тариф: **8 000 токенів/хв і 200 000 токенів/добу на модель**. За всі прогони eval: 85 викликів генерації, **282 відповіді 429** (135 добових TPD, 12 хвилинних TPM, 135 — до того, як я почав логувати тип ліміту) і **3 реальні випадки невалідного JSON** (Groq 400 `json_validate_failed` → repair-запит). Жоден тікет не загубився і скрипт не впав: тікет позначався «generation failed» → ⚠️ review, а повторний запуск дозаповнював лише пропуски з кешу. Висновок із прогонів, втілений у коді: **при добовому ліміті (TPD/RPD) retry марний** — клієнт одразу переходить до наступної моделі, а не чекає 7 разів по хвилині (unit-тест `test_daily_limit_skips_retries_and_falls_back`). У production — платний тариф і алерт на частку fallback'ів |

Тести детермінованої частини (пошук, перевірка цитат, regex обіцянок 4 мовами, рівні human judgment): [tests/test_assistant_checks.py](../tests/test_assistant_checks.py) — 15 тестів, + 14 тестів failure handling LLM-клієнта ([tests/test_failure_handling.py](../tests/test_failure_handling.py)), зокрема добовий ліміт без марних retry.

## 10. Caching

Тут кешування **має більше сенсу, ніж у Task 1**, бо один тікет = 3 LLM-виклики, а агент часто натискає «згенерувати» повторно.

| Що кешуємо | Де | Ключ / інвалідація | Навіщо |
|---|---|---|---|
| **Індекс BM25 і статті** | `@lru_cache` у `retrieval.load_kb()` | інвалідація — перезапуск процесу після зміни `kb/` (у production — версія бази знань у ключі / webhook з CMS) | не перечитувати й не переіндексовувати базу на кожен тікет |
| **Результат для того самого тікету** | `@st.cache_data(ttl=3600)` в [app.py](app.py) | ключ = текст тікету + модель + версія промпту; TTL 1 год | агент перемикає вкладки, клікає ще раз, колега відкриває той самий тікет — не платимо вдруге і не отримуємо **інший** варіант відповіді на той самий тікет |
| **Prompt caching провайдера** | автоматично в Groq для gpt-oss (−50% на кешований префікс) | system prompt статичний і стоїть першим; статті й тікет — в кінці | system prompt генерації ~700 токенів, аналізу ~250, класифікації ~1000 |
| **Проміжні результати eval** | `results/_stage1_cache.json`, per-model JSON | ключ = версія промпту аналізу + текст тікету | повторний прогін (після rate limit чи вимкнення світла) дозаповнює лише пропуски; порівняння моделей генерації на **ідентичних** класифікації й пошуку |

**Чого НЕ кешуємо:**
- **відповіді на «схожі» тікети** (семантичний кеш) — у двох схожих тікетах різні суми, дати, імена; чужа відповідь = витік даних або неправильна інформація;
- **довше 1 години** — база знань і політики змінюються, а стара відповідь з неактуальною політикою гірша за затримку в 5 секунд.

**Інвалідація при зміні бази знань** — головний ризик кешування тут: стаття про refund змінилась, а кеш віддає стару відповідь. У прототипі TTL 1 год обмежує шкоду; у production — включити хеш версії бази знань у ключ кешу.

Через обмеження часу (≈1 день на Task 2) й інструментів (безкоштовний тариф Groq) я свідомо зробив такі компроміси:

| Компроміс | Чому прийнятно зараз | Що зробити в production |

| **Regex для обіцянок refund** | безкоштовно, миттєво, 5 мов; ловить явні обіцянки | regex пропускає перефразування (див. розділ 4) — у production додати дешеву LLM-перевірку policy-compliance або класифікатор на розмічених прикладах |
| **langdetect для мови відповіді** | легка бібліотека | плутає uk/ru на коротких текстах — тому uk↔ru не сигналимо; краще — fastText lid |
